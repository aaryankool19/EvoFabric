# Waveform Verification Guide

This guide explains how to inspect EvoFabric simulation waveforms in GTKWave. The VCD files are generated by the SystemVerilog testbenches when you run `make test`.

## Generate Waveforms

```sh
make test
```

The generated VCD files are written to `waves/`.

Open a waveform:

```sh
gtkwave waves/tb_top_workload_switching.vcd
```

Useful starting points:

- `waves/tb_top_workload_switching.vcd`
- `waves/tb_bad_result_fallback.vcd`
- `waves/tb_adaptive_controller.vcd`
- `waves/tb_accelerator_interface.vcd`

## Reset Behavior

Open any accelerator or top-level testbench and inspect:

- `clk`
- `rst_n`
- `done`
- `busy`
- output registers
- counters/status registers

Expected behavior:

- `rst_n` starts low.
- State, status, and result signals initialize to known values.
- `done` is low after reset.
- `busy` is low after reset.
- Counters begin from zero or their reset values.

## Start/Busy/Done/Valid Handshake

Good waveform: `waves/tb_accelerator_interface.vcd`

Inspect:

- `start`
- `valid`
- `busy`
- `done`
- `cycle_counter`
- `accelerator_id`

Expected behavior:

1. The testbench asserts `valid` and pulses `start`.
2. The accelerator asserts `busy`.
3. After the operation latency, `busy` deasserts.
4. `done` pulses to mark completion.
5. `cycle_counter` records the operation latency for that accelerator.
6. `accelerator_id` matches the instantiated accelerator.

## Selected Accelerator ID Changes

Good waveform: `waves/tb_top_workload_switching.vcd`

Inspect signals under `dut.u_controller` and `dut.u_slot`:

- `opcode_reg`
- `selected_accel`
- `slot_id`
- `slot_start`
- `slot_done`

Expected behavior:

- A popcount request selects the popcount accelerator ID.
- A FIR request later selects the FIR accelerator ID.
- `slot_start` only launches the selected accelerator path.
- The muxed `slot_id` follows the accelerator selected by the controller.

## Mux-Selected Accelerator Output

Good waveform: `waves/tb_top_workload_switching.vcd`

Inspect:

- `selected_accel`
- `slot_o0`
- `checked_o0`
- `result_0`
- accelerator-specific outputs inside `u_slot`

Expected behavior:

- Only the selected accelerator's output is forwarded through the virtual slot mux.
- `slot_o0` reflects the selected accelerator result.
- If the safety checker passes, `checked_o0` matches `slot_o0`.
- On top-level completion, `result_0` captures the checked output.

## Safety Checker Pass/Fail

Good waveforms:

- Pass case: `waves/tb_top_workload_switching.vcd`
- Fail case: `waves/tb_bad_result_fallback.vcd`

Inspect:

- `mismatch`
- `fallback_forced`
- `slot_o0`
- `checked_o0`
- `result_0`

Expected pass behavior:

- `mismatch` remains low.
- `fallback_forced` remains low.
- Checked outputs match accelerator outputs.

Expected fail behavior:

- Fault injection changes the slot output.
- `mismatch` asserts when the checker compares against reference logic.
- `fallback_forced` asserts.
- `checked_o0` returns the trusted reference result.
- `result_0` captures the corrected checked result.

## Fallback Activation

Good waveform: `waves/tb_bad_result_fallback.vcd`

Inspect:

- `fault_inject`
- `mismatch`
- `use_fallback`
- `disabled_accels`
- `selected_accel`
- `result_0`

Expected behavior:

1. `fault_inject` flips one bit in the muxed accelerator output.
2. The safety checker detects the mismatch.
3. The controller records the selected accelerator as disabled.
4. A later request can use fallback rather than trusting the disabled accelerator.
5. The visible output remains the trusted reference result.

## Performance Counter Updates

Good waveform: `waves/tb_top_workload_switching.vcd`

Inspect:

- `total_cycles`
- `calls`
- `failures`
- `last_selected`
- `last_latency`
- `best_latency`
- `start_request`
- `ctrl_complete`

Expected behavior:

- `total_cycles` increments while the design is out of reset.
- `calls` increments when a new request starts.
- `last_selected` records the accelerator selected for the request.
- `last_latency` updates when the operation completes.
- `best_latency` tracks the best observed latency.
- `failures` increments when a mismatch or accelerator error occurs.

## Recommended GTKWave Signal Groups

For top-level debugging, group signals like this:

```text
Clock/reset:
  clk
  rst_n

MMIO request:
  bus_valid
  bus_write
  bus_addr
  bus_wdata
  bus_rdata
  bus_ready

Controller:
  opcode_reg
  start_request
  selected_accel
  op_active
  slot_start
  slot_done
  use_fallback
  disabled_accels

Safety:
  mismatch
  fallback_forced
  slot_o0
  checked_o0
  result_0

Performance:
  total_cycles
  calls
  failures
  last_selected
  last_latency
  best_latency
```

This makes it easier to connect software-visible MMIO writes to controller decisions, accelerator outputs, safety behavior, and counter updates.
